What this skill is

meta-skill-feedback is a meta-skill: it teaches agents how to add a runtime friction inbox to another skill, and how to use that inbox after a real job.

It does not edit your rules, task outputs, or the target skill’s behavior on its own. It wires structure + cues so surprises become reviewable notes.

Two production modes (not the same thing)

1 · Bootstrap Cody asks an agent to use the meta-skill-feedback skill to add a feedback system to a target skill.

The agent loads meta-skill-feedback, reads the target skill, then creates feedback/, feedback/README.md, feedback/resolved/, and a finish-line cue in that target’s SKILL.md (e.g. “Before you finish”).
2 · Runtime Agent finishes a normal job using a skill that already has feedback/.

If something non-routine misled them → write one timestamped .md file. Routine run → write nothing. Never edit the skill.

My Machines wake.md / wake.sh is a separate scheduling system. It is not part of meta-skill-feedback. If Cody wants feedback cues on unattended runs, he patches wake separately.

What the v0 evals test (PAC harness)

Evals live in evals/evals.json. They use the provider-agnostic-skill-creator loop in dotfiles (with_skill vs without_skill baseline). Fixtures under evals/fixtures/ are fake mini-skills — we never mutate real skills during evals.

Eval What we ask the agent to do What we assert Status
bootstrap-minimal Copy bare fixture → outputs/, then install feedback inbox using meta-skill-feedback. feedback/README.md, resolved/, cues in SKILL.md; no seeded friction files; no scaffold script. ran
runtime-quiet Copy already bootstrapped fixture; simulate a routine run with no surprises. No new friction .md; SKILL.md unchanged. pending
runtime-friction Copy trap-skill fixture — step 1 points at data/project.txt but file is at inputs/project.txt. Complete task; write one friction note; do not fix SKILL.md. Exactly one timestamped note; mentions path mismatch; has “What happened”; SKILL.md unchanged. pending

Important distinction:

  • Eval 1 tests bootstrap — “can an agent install the inbox correctly?”
  • Eval 2 tests runtime discipline (quiet) — “on a routine run, does the agent stay silent?”
  • Eval 3 tests runtime discipline (write) — “when misled, does the agent leave a note instead of editing the skill?”
  • Note quality (good suggestion, right tone) still needs human review in the PAC viewer — checks only cover structure.

With skill vs baseline (what “pass” means)

Each eval runs twice:

  • with_skill — executor reads meta-skill-feedback
  • without_skill — same prompt, no meta-skill (agent improvises)

scripts/check_eval_outputs.py checks filesystem facts; PAC aggregates into benchmark.md + review viewer.

Confidence & next steps

This is an early experiment. v0 proves:

  • Agents with the skill can bootstrap a minimal fixture reliably (5/5 vs 2/5).
  • We have deterministic checks + a PAC-shaped loop to iterate.

Still to prove: runtime-quiet discipline, runtime-friction writes, and (via human review) note quality on harder traps.
